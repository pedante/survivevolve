# M1 — OpenEvolve × MAgent2 Battle

**Status:** experimental integration. M1 does not implement autonomous organisms
or self-directed evolution spending. Red and blue are **two evolutionary
populations**, each with a Python policy shared by its MAgent2 team.

We reuse actual implementations:

- [OpenEvolve](https://github.com/algorithmicsuperintelligence/openevolve):
  real run_coevolution, two independent populations, archived programs and LLM mutations.
- [MAgent2](https://magent2.farama.org/environments/battle/): real Battle parallel
  environment, discrete actions, observation shape 13 × 13 × 5.
- Docker: each generated policy runs in its own restricted container.
  MAgent2 runs in the trusted referee process; candidate source is never imported there.

## Installation (Linux, Docker daemon required)

From the repository root, Python 3.12 recommended:

~~~bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
python -m pip install -e './survivevolve[dev,arena]'
docker build -f survivevolve/docker/Dockerfile.policy -t survivevolve-policy:m1 .
python -m pytest -q survivevolve/tests
~~~

The standalone Survivevolve package remains installable without OpenEvolve and
MAgent2; the arena is optional. OpenEvolve comes from this root checkout.

### 1. Real arena + real isolated workers, no model

~~~bash
python -m survivevolve.engines.openevolve_battle --smoke --cycles 6 --seed 17
~~~

A JSON score report labeled real_magent2_docker_smoke should appear. **No API calls.**
If the Docker image, daemon or MAgent2 is unavailable, stop; never disable sandboxing.

### 2. Real OpenEvolve with scripted proposals, no model

~~~bash
python -m survivevolve.engines.scripted_smoke --cycles 3
~~~

This exercises the actual OpenEvolve coevolution controller, MAgent2, and isolated
policy workers. A local dummy HTTP endpoint returns **scripted Python**. This is
not evidence of LLM intelligence or a fitness improvement. CI runs it without secrets.

### 3. Optional live model experiment (can cost money)

Only after the previous checks pass:

~~~bash
export SV_MODEL='YOUR_MODEL_NAME'
export SV_API_BASE='https://YOUR_PROVIDER/v1'
export SV_API_KEY='YOUR_KEY'
python -m survivevolve.engines.openevolve_battle \
  --confirm-live --rounds 1 --iterations 2 --seed 17 \
  --output results/m1-live-001
~~~

The API key stays in trusted OpenEvolve processes, never the Docker workers.
A run writes OpenEvolve checkpoints and a Survivevolve manifest with code hashes.
Set **provider-side spending limits**: iterations do NOT precisely bound requests
or charges. Resume requires identical manifest settings.

No actual LLM-produced improvement has yet been verified. That remains an
explicit experiment, not an implementation claim.

## Fitness

For each candidate, compare against every frozen historical opposing champion,
using matched seeds from both colors:

- game 1: candidate red, opponent blue
- game 2: opponent red, candidate blue

Fitness is mean(candidate reward minus opponent reward) across matched color
swaps, then the minimum score across opponent champions. Invalid candidate
actions/crashes/timeouts return -10000. Host code never imports generated source.
No held-out generalization metric or cost-adjusted net fitness is claimed yet.

## Safety and limitations

The container denies network, capabilities and additional privileges, uses a
read-only filesystem, non-root UID, CPU/memory/PID ceilings and a read-only
policy file mount. It is **not** a formal security proof. Prefer rootless Docker
or a VM/gVisor for actively adversarial models. Never mount keys, Docker socket
or referee inside a worker. The host OpenEvolve can execute *trusted evaluator*
code; only generated policy code is isolated here.

Future milestones: persistent individual identity, survival budget, organism
controlled evolution, N independent organisms, independent prompts, held-out
multi-arena evaluations and event replay.
